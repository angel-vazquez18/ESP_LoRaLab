# Documentation instructions

Read root instructions. Documentation must distinguish user decisions, selected
implementation choices, proposals, source-code behavior and measured evidence.

- `project_brief.md`: durable requirements and confirmed user decisions.
- `architecture.md`: implemented placement and proposed future module seams.
- `node_development_plan.md`: capability-based node roadmap; experiments are a
  coverage/validation reference rather than the definitive firmware implementation order.
- `status.md`: current consolidated capabilities, limitations and check results.
- `implementation_status.md`: imported detailed host status, including prior evidence.
- `experiment_implementation_checklist.md`: all 23 experiment implementation steps.
- `test_procedures.md` / `test_experiment_catalog.md`: full procedure obligations.
- `testbed_contract_v2.md` and root `contracts/v2`: selected protocol baseline.
- Root `CONTEXT.md`: domain glossary only; no architecture or implementation notes.
- `history/`: historical source context, not current agent instructions.

Use root-relative command examples, or explicitly state a different working
directory. Keep links valid after moves. Preserve CDR scope, historical evidence
provenance and outstanding physical/browser verification. Never mark an experiment
ready from a subset run or describe a stub as implemented.
